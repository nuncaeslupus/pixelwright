§1Problem statement

The M0–M3 build works piece by piece: CLI pw, providers, rule checks, a web viewer with four modes, an Aseprite bridge and Claude skills. As a product, though, it does not explain itself. After using it, the owner could not say what it is for, how it attaches to a real game project, which steps are done by scripts, which by AI and which by a person, or in what order the viewer's modes are meant to be used. A long help menu did not fix that, because the problem is the product's shape, not its documentation. pixelwright should do one job: take any image (an AI output, a hand sketch, a photo, someone else's art) and turn it into game-ready pixel art for a given project's style, in escalating steps (scripts, then an AI agent, then the person), keeping its history. Where the first image came from does not matter; improving it is the point.

Who uses it: one person making the art for a game. An AI agent does the reading, critiquing and fixing. The agent is not fixed: anything that can run pw and read images will do. Claude (Claude Code or Claude Desktop, on the person's own subscription) is the first-class one, and pixelwright uses its tools where they help, such as background waiting for app requests. There is no API key, so the app never calls an AI itself. Below, "AI" means that agent.

Success criteria (measurable):

  • [ ] A first-time user, given only the app, can state in one sentence what it does and name the next step at every screen without the help text (judged by the owner on a first run of a new build).
  • [ ] Every step of the flow (section 2.2) names exactly one actor (script, AI or person) and one place it runs (app, pw, AI session, Aseprite); no step is reachable by more than one main path (judged by review of the flow table against the app).
  • [ ] A project is an ordinary folder: deleting the app leaves every input, version, advice entry and final image readable as plain files (png, toml, jsonl), verified by a test that opens a project with no app installed.
  • [ ] No version is ever overwritten. With "keep all versions" on (the default), versions_written == versions_on_disk after any sequence of accept/reject/edit actions; with it off, the input, the first version, every starred version and the final are still kept (tests).
  • [ ] Opening an existing project folder of 50 assets shows the asset list in <= 2 s on the owner's Linux machine.
  • [ ] Normalising one 320×180 input (resize, palette, grid, clean-up) takes <= 5 s without the AI.
  • [ ] A request left in the app reaches a listening AI session within <= 10 s, and costs no AI usage while nothing is pending (test with pw wait).
  • [ ] Approving an asset copies its final image to the project's configured export path, which can point anywhere, including inside a game engine's project (test).
  • [ ] The app and core run on Linux; nothing in the core depends on Linux-only libraries, so a Windows build needs packaging work only (checked by running the core test suite on Windows in CI).

§2Systems & Impact

§2.1Concepts

Concept What it is On disk
Project The art for one game. Holds the style: a palette library, canvas sizes, rules, references, export path. A folder with pixelwright.toml and style/
Palette A named colour set. A game uses several (backgrounds, characters, a night variant). A group sets a default palette; an asset may override it or use more than one. style/palettes/*.gpl
Asset One piece of final art: a background, sprite, portrait or animation. A subfolder under assets/
Group Related assets (a scene, a character, all backgrounds). Can set defaults such as the palette or canvas size. Parent folders (optional group.toml), plus optional tags
Input Any image the asset starts from or borrows from. inputs/
Version Every change makes a new image; none is ever overwritten. Old versions are the history ("this is what the character first looked like"). A project setting, "keep all versions" (on by default), can be turned off to keep only the input, the first version, starred versions and the final. versions/v001.png, … (plus .aseprite when edited by hand)
Advice One observation on one version: what is wrong, where (region), why (rule or reason), proposed fix, author (script, AI, person), state (pending, accepted, rejected + reason). One line in advice.jsonl
Request A piece of advice addressed to the AI from the app ("look at this outline"). Advice with author person, target ai, state pending
Final The approved version, copied to the export path. final.png

Storage of versions. Versions are plain indexed PNG files, readable by any tool. Pixel art compresses well: a 320×180 indexed PNG is typically a few KB, so a thousand versions are tens of MB. Delta storage (keeping only the changed pixels against the previous version) is possible and is deferred: design measures real sizes, and deltas are added only if a project grows past a set budget, still without losing plain-file readability of the final and starred versions.

Accepting advice applies its fix and creates a new version. Rejecting advice with a reason is recorded, and that reason can be promoted to a project style rule, so the same advice is not given again.

§2.2The flow

# Step Actor Where In → Out
0 Define the style (once per project) Person + AI, in conversation AI session References, intent → pixelwright.toml, style/
1 Brief + starting image Person (or the AI generates one, optional) App, AI session, or dropping files in inputs/ Text + image → inputs/
2 Normalise Scripts pw Input → v001 (size, palette, grid, clean-up)
3 Check rules Scripts pw Version → advice by script
4 Critique and fix AI, in a bounded loop AI session using pw Version + advice + brief → advice by ai + new versions
5 Decide Person App Before/after + advice → accept / reject / own notes / request to the AI / open in Aseprite
6 Approve and export Person decides, scripts copy App or pw Version → final.png + copy at export path

Steps 3–5 repeat until the person approves. A round moves up a step only when the cheaper one was not enough: scripts always run; the AI runs when rule advice remains or the person asks; hand editing in Aseprite is the last resort.

The AI bridge. The app cannot call an AI, so requests wait in the asset's advice log. The AI picks them up in one of two ways: - Listening. In an open session, the AI runs pw wait in the background. It blocks until a request appears, then returns; the AI handles the request and starts listening again. Claude Code supports this directly through its background tasks. - On demand. The person says "check pending". With Claude, a session-start hook also says how many requests are waiting.

§2.3Inside and outside

Inside pixelwright: - Project and asset structure - Normalising - Rules and advice - Versions - The app - Export - The request queue - Agent instructions that teach the flow (Claude skills first; a plain AGENTS.md for other agents)

Outside (plugged in, optional): - Image-generation models (providers) - Aseprite, for hand editing - The AI agent, as the conversation - The game engine, which only receives files at the export path

§2.4Folder layout (starting point, adaptable)

my-game-art/                    project
  pixelwright.toml              style + export path
  style/                        palettes/*.gpl, references, style notes
  assets/
    scenes/                     group (optional group.toml: default palette, size)
      harbour-night/            asset
      asset.toml                brief, state, chosen version
      inputs/
      versions/                 v001.png v002.png ...
      advice.jsonl
      final.png
  export/                       default export path; may point into the engine project instead

§3Options

▸Option A: Keep the current shape, add a guided mode (Conservative)

  • Description: Leave the CLI, workspace and four-mode web viewer as they are, and add an in-app guided walkthrough on top.
  • Scope: Viewer only.
  • Effort: Small
  • Tradeoffs: Cheapest, but treats a shape problem as a documentation problem, which the help menu already showed does not work.
  • Compatibility: Full.

▸Option B: One flow around a project folder, desktop app for decisions (Recommended)

  • Description: Re-centre everything on the project-folder / asset-folder model and the six-step flow. The core (pw) does every automatic step. The AI works through pw from its own session and the request queue. The app is a pywebview desktop window that opens a project folder, used to brief, decide and approve.
  • Scope: Core model, app, skills, first-run; providers and the Aseprite bridge mostly kept.
  • Effort: Large
  • Tradeoffs: Fixes the root cause and makes the AI/script/person split visible; costs a rework of the viewer and the workspace model.
  • Compatibility: Breaks the M0–M3 workspace layout; no external users, so no migration is needed beyond the owner's test assets.

▸Option C: Aseprite plugin as the only interface

  • Description: Drop the app; show advice and approve inside Aseprite.
  • Scope: Core + Aseprite plugin.
  • Effort: Medium
  • Tradeoffs: No new app, but Aseprite's plugin UI is too limited for browsing a project and comparing versions, and it ties the tool to one editor.
  • Compatibility: Breaks the viewer.

▸Comparison

Option A Option B Option C
Effort Small Large Medium
Risk High (does not fix the problem) Medium Medium
Completeness Low High Medium
Compatibility Full Breaks workspace layout Breaks viewer
Maintenance Grows (two shapes) One shape Editor-bound

§4Recommendation

Recommended option: Option B. It is the only option that answers the original problem (what it is for, who does each step, where it runs), and the core, providers and Aseprite bridge carry over.

Immediate next action: After this spec is approved, run design for sections 5–6: the project/asset/advice file formats, the pw commands of the flow, pw wait, the pywebview app and its screens, then a reuse map of M0–M3 code.

Open questions: - [ ] Game engine: a short survey of adventure-game and general engines after this spec; until then only a configurable export path (D-4). - [ ] App sub-name: plain "pixelwright", or a sub-name such as "pixelwright Desk" (minor; the owner accepts either).
