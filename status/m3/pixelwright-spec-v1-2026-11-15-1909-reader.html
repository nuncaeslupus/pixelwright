§1Problem statement

After M2, pixelwright can clean, check, critique and review an image, but it cannot make one: every image has to come from outside (pw attach). The painter half of the pipeline (main spec §2.1, "image models paint") is missing, so the loop the tool is built around has never run end to end.

The second problem is understanding. The artist has used the viewer and the Aseprite bridge but says the tool does not make sense yet as a whole. The commands are many (about 40) and each one is small; nothing shows how they chain into "sketch in, game-ready pixel art out", or what to do next at any point. A tool that only its author's Claude understands fails the main spec's goal of the artist sketching, approving and retouching.

▸Success criteria

  • [ ] pw tour runs the whole loop (new, attach sketch, generate, snap, quantize, clean, check, critique, review in the viewer, approve, export) on a bundled sample, offline, with no GPU and no API key, in <= 60 s of machine time; each step prints what it did, why, and what to look at, in plain words.
  • [ ] Every command's --help and every viewer screen with nothing to do answers "what next?": pw next <id> names the next step for an asset from its state, and the viewer shows the same hint.
  • [ ] pw generate <id> --provider <p> makes 1-4 candidate versions with the provider, request, seed and cost in each meta.yaml; the same request twice is a cache hit that costs 0 and gives byte-identical files.
  • [ ] Budget: a call that would exceed the workspace's monthly budget is refused before it is sent (exit 6); every paid call appears in pw cost with its price.
  • [ ] Local route: the ComfyUI adapter generates a 320x180 background from a sketch on the owner's machine (img2img, Flux or SDXL with a pixel-art LoRA), checked by a prompt the owner runs locally.
  • [ ] pw regen-region <id> --issue <n> repaints only the issue's mask with a provider that supports inpainting; pixels outside the mask are unchanged (byte compare).
  • [ ] Benchmark: the main spec's criterion (3 generators x 2 chains x 3 briefs x 3 samples, <= 20 USD, detector scores, Claude pairwise, blind human pairwise ranked with Bradley-Terry) produces benchmarks/<date>/report.html, and its result sets the default provider per asset kind in pixelwright.toml.
  • [ ] CI stays offline: every adapter is tested against recorded responses; no test needs a key, a GPU or the network.

  • Artist: learns the loop from pw tour and the guide; decides which paid providers to use.

§3Options

▸Option A: Paid APIs first

Build the Gemini, Retro Diffusion and PixelLab adapters first, then the benchmark, then the local route and the tour.

  • Pros: pixel-native providers (Retro Diffusion, PixelLab) may give the best raw output fastest.
  • Cons: needs keys and money before anything runs; the tour and CI would depend on recorded responses from paid services; the artist still cannot see the loop until late.

▸Option B: Learn first, local first, then paid (Recommended)

Order: provider framework with the offline replay provider and pw tour (the loop runs end to end on day one, for free), then the local ComfyUI route, then regen-region, then the paid adapters the owner chooses, then the benchmark that picks defaults.

  • Pros: the artist sees and understands the loop first; the first real generator is free and licence-clear (main spec D-12); paid spend waits for the benchmark, which needs only the 20 USD already approved.
  • Cons: ComfyUI setup on the owner's machine is a manual step; pixel-native paid providers are tried later.

▸Option C: Every adapter at once, no tour

Build all six adapters in parallel, then the benchmark; leave onboarding to docs.

  • Pros: fastest to a complete benchmark.
  • Cons: does not answer the understanding problem; most adapter code would be written before knowing which providers are worth keeping.

§4Recommendation

Option B. Milestone order inside M3:

  1. M3a, understand: provider framework (protocol, registry, cache, budget, cost ledger, secrets), the replay provider, pw generate, pw next, pw doctor, pw tour with a bundled sample (sketch and "painted" image drawn procedurally in the repo, so no third-party art), docs/guide/how-it-works.md, the viewer hint, the first-run skill.
  2. M3b, local: ComfyUI adapter (txt2img, img2img, inpaint) with workflow presets for Flux and SDXL plus a pixel-art LoRA, a setup guide, regen-region, candidates in Compare.
  3. M3c, paid and benchmark: the paid adapters chosen in D-M3-1, pw bench run/report, the blind pairwise page, Bradley-Terry ranking, defaults per asset kind.
